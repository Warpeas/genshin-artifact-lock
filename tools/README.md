# tools/ —— 配装数据抓取与回写工具链

配装数据**只**来自米游社「观测枢」wiki 角色词条里的结构化表格（wiki 编辑手填文本）。
词条里另外挂着的米游社攻略文章几乎全是图片一图流，本工具链**不从图片里解析词条**，
只在 `out/sources.*` 里作为人工延伸阅读列出。

> 例外：`fetch_guide_subtiers.py` 会**下载**攻略图给人看（不解析、不回写 `src/data.js`），
> 用于交叉校准词条优先级。见下文「副词条分级校准」。

> **一条命令重建**：`python tools/rebuild_data.py`。
> 联网抓取与离线快照重放走的是**同一套** `STAT_ALIAS` / `TOKEN_ALIAS` / `parse_fields()`，
> wiki挂掉也能用 `--offline` 从 `tools/out/wiki_builds.json` 快照重放出一致结果。

## 副词条分级校准（`fetch_guide_subtiers.py`）

观测枢给的是**平铺**词条列表，攻略图往往给带分级符号的顺序（`暴击、暴伤 > 攻击% > 充能`）。
本脚本把攻略图抓到本地供**交叉校准**，**不解析、不自动回写** `src/data.js`。

- **入口**：`getPostFull` 的 `post.content` 对一图流是**空字符串**，唯一入口是 `post.image_list`。
  图片下载无需鉴权，仅需 `User-Agent` + `Referer: https://www.miyoushe.com/`（CDN 防盗链）。
- **只做两个作者**：`Asgater`（优先）> `HoYo青枫`。两者都是高密度模板化一图流。
- ⚠️ **圣遗物页位置不固定，绝不可硬编码 image下标**。实测 Asgater：
  桑多涅 25 张在 index **7**、奥黛塔在 **8**、丝柯克在 **7**、阿罗夏在 **5**；
  同一篇里 index 5/6 往往是「参考面板」「武器期望」。可靠信号是**页面里有「圣遗物搭配」
  或「属性需求」标题栏**（后者明确分时之沙 / 空之杯 / 理之冠 / 副词条四段）。
  所以脚本策略是「抓候选页 range(2,10) + 人工确认」，`artifact_page` 由识别阶段回填。
- **选篇要挑结构标准的**：同一作者可能有多篇，「全面解析︱养成/配队/机制」长篇
  （23~25 张、含 1181×1012 武器期望图）才是完整模板；「一图流」短篇可能只有 3~4 张、**没有圣遗物页**。
  `pick_guide()` 按「张数 ≥12 且含 1181×1012」打分选取。
- **依赖**：裁切/缩略需 `Pillow`（隔离安装：
  `python -m pip install --target=<envs>/default/pylibs pillow`，跑时带 `PYTHONPATH`）。
  不装Pillow 也能跑，只是不做裁切。
- **产物**：`out/guide_subtiers/<角色>.json`（含每页的本地路径 / 原始 URL / 尺寸）
  + `_manifest.json`（批次清单）。`out/guide_subtiers/_read_result.json` 是人工/模型读图后
  结构化的结果（`_cross_check.py` 会拿它跟 `wiki_builds.json` 对照）。

### 两个模板的副词条写法（实测）

| 作者 | 分级符 | 示例 | 可读性 |
|---|---|---|---|
| **Asgater** | `>` 分档，同档内逗号并列 | `暴击、暴伤 > 攻击% > 充能、精通` | 好 |
| **HoYo青枫** | `↓` 箭头串联，**每档只一个** | `暴击、暴伤 ↓ 生命值 ↓ 元素精通` | 更好（版式固定三行） |

HoYo青枫 的版式高度统一：1772×6320 超长图，圣遗物区固定在**45%~56% 高度**，
副词条永远是「首档两项 + 单箭头 + 第二档 + 单箭头 + 第三档」的三行结构。
但**档位内容按角色定**，不是套模板 —— 实测胡桃=生命值、流浪者=攻击力、提纳里=元素精通。

⚠️ **主词条可能与 wiki 顺序相反**：胡桃图里写 `时之沙：元素精通/生命值`，
而 wiki 是 `sands:['hpP','em']`（生命在前）。这类分歧要人工判定谁对，不要机械覆盖。

### ⚠️⚠️ 版式有 7 种，绝不要预设候选页范围

实测圣遗物页下标与图片尺寸**完全不固定**，任何硬编码 / `range` 都会整批漏读：

| 版式 | 特征 | 圣遗物区 | 分级命中率 |
|---|---|---|---|
| **L1 短篇长图** | 4张，含 1260×29xx 长图 + 4902×3440 材料图 | 长图的 52%~66% | **11/15（73%）** |
| **L2 新版单页图文** | 每页一主题，标题在左上角大号艺术字 | 页序第 3~8 页不定 | 3/17，但 14/17 带编号条件面板 |
| **L3 月之N 系列** | 「月之一~八」全面解析，1080×2xxx 长图 | p1 的 44%~66% | 1/4 |
| **L4 1280 多页标准篇** | 8~39 张 | index 5/7/8 各不相同 | 0/2 |
| **L5 超长单图** | 1890×4833 | 50%~64% | 1/1 |
| **HoYo青枫 老版** | 1772×63xx / 7461 | 45%~56% | 5/5（100%） |
| **HoYo青枫 新版图文** | 2363×3147 + 1181×5496 | **只有套装、没有词条** | 0/5（结构性缺失，直接跳过） |

→ 脚本已改为**全量抓所有非窄条页**（`all_but_strip: (900, 400)`）。代价是磁盘占用，换来绝不漏读。

### 读图提效三招（`_` 前缀脚本，本地自用）

1. **`_title_strip.py`** —— 取每页**顶部 40%** 横向拼成标题条，一眼认出「圣遗物搭配」在哪页。
   ⚠️ 取 22% 不行（被角色立绘挡住）；⚠️ 最新版式标题在**右上角**，标题条会误判。
2. **`_probe_bands.py` / `_probe_all.py`** —— 长图按比例切段 + 标尺（`0%-10%`…），一次定位再裁细。
3. **`_batch_sub_crops.py`** —— L1 短篇长图版式统一，可批量裁切 + 拼联络表（`_subs/_grid.jpg`），15 段一张图读完。

**坑**：联系表缩略会骗人（菲林斯 #2 看着像圣遗物页实际是养成分析）。写完读图 JSON **必须 `json.load` 校验**——中文 JSON 极易漏掉值上的引号。

## 配装条版式 Playground（`tools/playground.html`）

角色卡配装条（`.cc-bp`）的**版式调试台**：把 S1a（已落地）/ S1c（balance）/ S2（能同行就同行）/
S2 +balance 等方案的 CSS 规则各挂一个开关类，五张卡用**同一套内容**纵向排布、卡宽统一由滑块控制，
改【名字长度】【定位词条数】【视口宽度】即时看到各方案差异，不必反复改 CSS + build + 截图。

- **直接双击打开**（单文件、零依赖、file:// 可用），也可以 `python -m http.server` 起服务后访问。
- **每个方案一张等宽卡、一卡一框**（纵向排布），框里就是上面【名字】【定位】两栏的内容 —— 方案之间唯一的变量是版式规则本身。
  点方案名弹小窗看该方案的设计简述、实测数据与已知代价。
- **滑块控制的是「角色卡内容区宽」（120–300px，默认 150）**，不是视口宽 —— 早前那版走
  「模拟视口 → `.char-grid` auto-fill → 反推行宽」，结果每加一张卡列宽就变、既不直观也不精确。
  断点因此改为按卡宽判定：`#stage.vpn` ≤176px / `#stage.vpw` >176px。
  **176 是唯一能让所有真实卡宽都判对的取值** —— tools/out/_cw.mjs 在真实 `index.html` 上量到
  卡内容区宽是离散跳跃的：窄屏档（视口 ≤560）130/140/149/155/165/175，宽屏档（≥561）177/199/200/221/237/239/258/266/272/283，
  中间只空 176px 一档。⚠️ 卡宽↔视口**不是单调映射**（320 视口 272px > 340 视口 130px），
  任何「按卡宽自动推断点」都有误差，176 是误差最小的取法。
  取 160 会把 160–220 整段落给宽屏同行版式，出现「同行版式 + 极窄卡」的假象：
  定位栏被名段挤到 ~79px → 定位被迫折 3–4 行，**真实页面 492 行 × 16 档实测 3 行 = 0 条**。
  `@container` 保持原生（`container-type` 在 div 上照常生效，量的就是卡内容区宽）。
  快切按钮按**视口**给（点一下 = 该视口真实的卡宽 + 真实的断点档）。
- **词条滑块上限 5 = 真实上限**（3 大类 + 2 关键词）。tools/out/_mw.mjs 量到真实定位整段
  最长 126.3px；上限放到 6 会造出 185.6px（比现实长 47%）的定位，配上虚构卡宽就成了双重假象。
- 舞台内的 `.cc-bp` 规则是从 `src/styles.css` 复刻并加 `#stage` 前缀的版本；
  **改 `src/styles.css` 的配装条规则时，同步改 `playground.html` 里的同一份**，否则调试结果会失真。
- 宽屏的 `.nmwrap`（名段折行 → 定位独占下行）由 JS 打类，与 `app.js markWrappedBuildNames()` 同口径。
  判「名段是否折行」必须用 `Range` 逐字符扫按 top 归并 —— `.cc-bp-name` 是 flex item（会被 blockify），
  `getClientRects()` 只返回一个整块 rect，量不出行数。
- 「演示：balance 生效场景」按钮可一键跳到「定位会折行」的工况（卡宽 140px ≈ 360 视口 + 6 词条）。
  该工况下（批量量测口径见 `tools/out/_bal.mjs`）S1a 两行长度差 **55%**、S1c **21%**、S1b **38%**（且拆词）。
- **自定义方案卡**：控制面板下方有 5 组分项复选框（定位段版式 / 名段折行 / 定位段 / 窄屏宽度 / 宽屏分档），
  勾选即时应用到「自定义」那张卡。成对互斥项自动二选一（`t4`↔`fit`、`n2auto`↔`n2fix`、`ladder`↔`lad7`）。
  点「一键复制方案」把**开关串 + 与 `src/styles.css` 等价的 CSS + 落地前复核清单**复制到剪贴板 ——
  这是给 AI/agent 反馈配置用的通道（粘过去就能直接落地）。旁边有「载入现行 S3 / 载入 S2 / 全不勾」三个快捷。
- **X 方案卡**（主人 2026-10-05 给的版式约束）：把 7 条要求收敛成 **5 条规则**，拆成 5 个自定义开关：
  `xsame`（位允许内部换行 → 短名+长定位时「名」与「位的第一行」同行）、`xbox`（框长可变 fit-content）、
  `xgap`（间隔 clamp 上下限）、`xcap`（单内容 ≤ 框长 90%）、`xpretty`+`xbar`（名填满首行 / 位按 ｜ 断行）。
  规则与主人原文的对应：①框长可变(1) ②间隔 clamp(2) ③90% 上限(5) ④短名长定位时首行同行(4/7) ⑤换行优先级(6)。
  ⚠️ **主人澄清过：「重叠」不是让名与位交叠，而是「各占各的行、不超过最大限制就行」** ——
  早前误读成「负 margin 水平交叠」与「row-gap 负值压叠」两个开关，已删除。
  `xgap` / `xcap` 需要一小段逐行 JS（间隔随剩余空间 clamp、90% 相对框宽，CSS 表达不了），
  引擎 `layoutSx()` 在 `render()` / `applyWidth()` 之后**同步**调用。
  ⚠️ **同行判据**（主人 2026-10-06 指出后修正）：不能用「名会不会折行」——
  8 字名（112px）配 5 词定位时名的自然宽没超 90% 上限 → 旧判据说「不折 → 同行」→
  定位只剩 ~30px、每个词单元各占一行，整块定位「往中间偏」。正确判据是
  **「名占掉一部分后，剩下的宽度还要放得下定位开头两个词单元」**才允许同行，否则定位独占第二行。
  ⚠️ 也不能用「定位第一行放不放得下」：每个 `.bt-w` 后面都跟一个 `<wbr>`，
  按第一个 `<wbr>` 量到的「第一行」永远只有一个单元（量出来 24px 而非 82px）。
  ⚠️ **90% 上限 + 右对齐的分工**（主人 2026-10-06 截图指出「勾了 90% 定位就偏了」）：
  `max-width:90%` 只是限宽，盒子仍**从左边起摆** → 右边反而空一截，看起来完全没右对齐。
  正确分工：**间隔加在【名段右边】**（`margin-right`，引擎算 clamp 值），
  **定位段用 `margin-left:auto` 靠右摆**（同行与落行都要 auto —— 落行时若归 0，同样会靠左偏）。
  这样 90% 的语义才成立：**右边贴框尾，最多向左占 90%，左边留 10%**。
  ⚠️ **同行门槛**（`xsame3`，默认开）：门槛 = 定位**前 3 个词单元**的宽度和（≈104px），
  保证「同行时定位 ≤ 2 行」。实测取舍：150 卡宽 +「苍白之火」+ 5 词 → 余量 66.8px < 104 → 落两行（定位 2 行）；
  而 2 单元门槛（62.1px）会强行同行、把定位压成 3 行。**这是物理上限**：
  155 卡宽 +「如雷」+ 5 词只剩 99.8px，差 4.2px 排不成 2 行 ——
  该工况只能二选一：落两行（位 2 行）或强行同行（位 3 行）。面板关掉 `xsame3` 即「强行同行」档。
  ⚠️ **min-width 会把盒子撑宽 → 表现为「间隔失控」**（主人 22:16 截图）：
  定位是右对齐的，一旦 `min-width`（同行下限 `--tg-min`）大于内容宽，盒子就被撑宽，
  撑出来的空白**全部落在文字左边** —— 237 卡宽实测：内容 101.4px / 盒 133px →
  名到文字 49.6px（其中 32px 是空白、14px 是名右边距）。
  两个修法（都做了）：
    1. 定位段 `flex-grow:0`（盒宽 = 内容宽），剩余空间交给「按钮收缩」消化；
    2. `--tg-min` 取 **min(三个词单元+间隔, 整段内容宽)** —— 对测量误差免疫。
  修后 237 卡宽：名→文字 18px、按钮收缩到 190.5px，与 S2+balance 的 12px 同量级。
  ⚠️ **`xsame` 的实现口径**（2026-10-06 重做，名义规则版）：
  `.cc-bp-tag{flex:1 1 min-content; min-width:var(--tg-min,0)}` —— 一条规则同时表达
  「定位首行能放多少放多少」：
    · `flex-basis:min-content` → flex 换行判定只看「名右边放不放得下最长的那个不可拆词单元」；
    · `min-width: var(--tg-min)` → 引擎给的下限 = **定位前 3 个词单元 + 间隔下限**（≈104px），
      放不下就整段落下一行（独占整行），放得下就同行并吃剩余空间、内部折行。
  之前用 JS 写 `tg.style.flex = '1 1 0' | '1 1 100'` 做二选一 —— 每个工况都要单独调参，
  是「特例修复」；现在判定交给 flex 算法，JS 只提供有含义的下限值。
  实测临界（名「苍白之火」+ 5 词定位）：卡宽 ≥186px 时「名 + 定位第一行」同行、定位 2 行；
  ≤175px 落两行、定位 2 行 —— 两种形态下定位都不超过 2 行。
  ⚠️ `xsame` 的另两个实现要点：① 只写 `min-width:0` 没用 —— flex 换行判定用的是**假想主尺寸**
  （由 flex-basis 决定），`basis:auto` = 内容宽 → 即使 shrink 后放得下也先判「放不下」而整段换行，
  必须 `flex:1 1 0`；② 选择器必须与 `k-fit` **同特异性且在其后** ——
  `k-fit` 那条含 `.vpn` 也是 1 个 class（共 5 个），所以 xsame 要写
  `#stage .cc-builds.k-xsame .cc-bp:not(.wide) .cc-bp-tag`（同样 5 个 class）才压得住。
  ⚠️ 引擎取容器要用 `bp.closest('.cc-builds')` —— 按钮外面还包了一层 `.bprow`，
  用 `parentElement` 会拿到包装层、类名判定全部落空（引擎静默不生效）。
- ⚠️ **90% 上限在同行与落行时都要施加**（我中间取消过一次，方向错了 —— 主人 2026-10-06 指出
  「X 的定位超过了一行总长的 90%」）。**90% 正是「位首字落在框宽 10% 处」这个机制**，
  也就是主人那条「定位首字要在名首字右移半字之后，以免定位看着像圣遗物名的换行」的实现：
  166 卡宽实测 → 位宽 128.6、右对齐后首字比名首字右移 **61.1px**，两栏起点明显错开 ✔
  （若不限宽，位占满 156px、右对齐后首字反而比名首字**左 7.7px** —— 正是主人看到的「像名的换行」）。
  代价：位自然宽约 150px > 128.6px → 折两行（主人明确接受：「否则再加个词折到第二行去」）。
  同行可行性还有物理上限：166 卡宽只剩 82.8px（定位需 ~150px）→ 强行同行必然折 2 行；
  要「同行且一行」需卡宽 ≈ 名 56 + 编号 9 + gap 4 + 定位 150 + padding 10 ≈ 229px。
- ⚠️ **90% 上限只给定位段、不给名段**（主人 2026-10-06 两次指出）：名是左对齐的，
  宽度上限该由 CSS 的 `.nfull/.n2` 给（`calc(100% - 编号列 - gap - padding)`，已防压编号）；
  再叠一层 90% 会比 S2 少几个 px —— 实测 140 卡宽下 108.8px vs 105.2px，
  「苍白之火 / 昔时之歌 /」就放不下、多折一行（3 行 vs S2 的 2 行），正是「第一行没放满」的观感。
  90% 的语义落在右对齐的定位段上：从右往左占、最多 90%、右边贴框尾。
- ⚠️ `text-wrap:pretty` 与「填满第一行」**相反**（默认不勾）：它会把长名均衡成多行；
  主人要的是贪心换行（第一行尽量多放、后续行递减）。面板里保留该开关仅供对照。
- **开关按「语义效果」分 8 组**（2026-10-06 收拢）：①框的长度 ②名与位是否同行 ③名↔位间隔
  ④单行长度上限 ⑤重心位置 ⑥换行策略 ⑦窄屏宽度策略 ⑧名段折行。
  每条规则只由自己的开关决定、互不影响 —— 之前引擎入口写了
  `if (!on('xgap') && !on('xcap')) continue`，取消这两个开关会连带把 `xsame` 的同行下限也关掉，
  出现「定位莫名变 3 行」的名义规则之外的现象。已删除该守卫。
  下线的开关：`t4`（强制两行，已被现行口径取代）、`tagbreak` / `gap8`（红线与重复项）、
  `ladder` / `lad7` / `nm`（宽屏专用，窄屏工作台用不到）、`n2fix`、`xsame3`。
  说明文字改成悬停 `title`（内联展开会把面板撑到两屏，一屏看不全等于没分组）。
- **两个行长上限分开、可调**（主人 23:01 定）：面板新增两个滑块 ——
  「名·从框左数」默认 100%（50–100%）、**「位·从框右数」默认 85%**（50–100%），
  **各自对应面板 ④ 组里的一个独立开关**（`xcname` / `xcap`），互不干涉。
  百分比直接交给 CSS 算（`--nm-cap` / `--tg-cap`，浏览器对 % 的基准就是框内容宽，
  比在 JS 里换算稳 —— 第一版在 JS 里换算，`avail` 取值口径与 CSS 基准不一致，70% 算出 99.4%）。
- 内容滑块扩容：名字 1–30 字（`composeName` 按需循环取套装名，用 ` / ` 分隔）、
  定位 1–10 词（`unitsByCount` 循环取词；**真实数据上限是 5 词 = 3 大类 + 2 关键词，
  >5 属压力测试**，面板上已标注）。
- ⚠️ **`flex-wrap` 必须挂在 `xsame` 上，不能只挂在 `fit`**（主人 22:46 截图）：
  fit 与 xsame 在面板里互斥，勾一个会取消另一个；而 `flex-wrap:wrap` 原本挂在 fit 上
  → 只勾 xsame 时按钮仍是 `nowrap`，定位永远与名同行、盒宽超出剩余空间，
  文字被推到按钮最左端（就是主人看到的「定位行超出圣遗物名的第一个字」）。xsame 的语义
  本身包含换行能力，所以这条规则归它。
- ⚠️ **「首字右移半字」不是独立规则，就是位的百分比上限**（主人 23:20 澄清）：
  我曾额外加一条「位首字要落在名首字右移半字之后」的 px 上限（`--tg-cap-name`），
  主人指出那正是「位 ≤ 框长 N%」的效果 —— 比例调小，首字自然右移。
  独立的 px 上限已删除，现在**位只有一条规则：从框右往左数 ≤ N%**（面板滑块，默认 85%）。
- **自定义卡的三个易错点**（都踩过）：
  1. 拼类名要补 `k-` 前缀：复选框 key 是 `fit`/`pad4`，样式类是 `k-fit`/`k-pad4`；
     漏了前缀 → 所有开关静默失效（表现像「复制方案没效果」）。
  2. 90% 上限要用「名+位可用总宽」而不是整个 avail —— 先扣掉编号徽标宽与 column-gap，
     否则「编号 + gap + 0.9×avail」超出可用宽，名段被挤到按钮左边界之外（压编号）。
  3. 「载入某方案」改为**从该方案卡的 flags 派生**开关（`presetFrom(id)`）而不是手写列表；
     手写漏了 `k-pad4`（横向内边距 6 → 4px）就会差 2px 内边距、断行点对不上。
     `pad4` 不在面板开关里（它是默认项），但必须列进 `FLAG_CSS`，否则派生时被过滤掉。
- 名字滑块拉长时按**真实套装名**逐个累积并用 ` / ` 分隔（`composeName()`），
  与数据里「多套任选」的名写法一致（少女 / 海染 / 昔时（任选2套)），不是一串连续汉字。
- `lad7` = **每字一档**实验档：`nameLadder` 改 7 档（2 字→1 … 7 字以上→7），
  阶梯 7.5/8.5/9.5/11.5/12.5/14/17.5em（窄屏 53/60/67/84/91/100%）。
  阶梯是按「名段实测自然宽 + 约 60px」估的，**尚未全量实测撞档率**，落地前必须重拟。
- 方案出处与取舍理由见 `docs/待探讨方案.md`；全量批量量测脚本见 `tools/out/_bal.mjs`（gitignored）。

## 标准流程（以 `rebuild_data.py` 为唯一入口）

日常重建**只需要跑这一条**：

```bash
python tools/rebuild_data.py               # 联网抓 125 角色 → 复核 → 回写 → 回归测试 → 自检 → 打包
```

它按固定顺序做 6 件事，任一步不通过即中止并返回非 0 退出码：

1. **联网抓取** `fetch_wiki_builds.py`（抓完自动跑一次 `--reparse` 复核，见「抓取门禁」）；
2. **回写** `apply_wiki_builds.py --no-links --apply`（写回 `src/data.js`）；
3. **解析回归测试** `test_parse.py`；
4. **数据自检** `check_data.js`（抓死字段 / 空 roles / optional 异常 / 未识别片段）；
5. **打包** `node build.js`；
6. **打印本次重建结果**（死字段 / 空定位 / 未识别片段 / optional 异常 / ★必选为空组数 / 自检退出码）。

最后仍会输出这四行门禁统计，只要非 0 就说明数据不干净。

### `rebuild_data.py` 常用开关

| 命令 | 含义 |
|---|---|
| `python tools/rebuild_data.py` | 默认：联网抓全部角色 → 复核 → 回写 → 自检 → 打包 |
| `python tools/rebuild_data.py --offline` | **不联网**：直接拿 `out/wiki_builds.json` 快照重放，结果与联网一致 |
| `python tools/rebuild_data.py --dry` | 只预览（不写 `src/data.js`，跳过自检与打包） |
| `python tools/rebuild_data.py --no-build` | 跳过 `node build.js` |
| `python tools/rebuild_data.py 胡桃 钟离` | **只重建指定角色**（联网时生效；离线时对快照整体重放） |
| `python tools/rebuild_data.py --allow-unrecognized` | 显式放行未识别片段（默认拦截，见下） |

**wiki 不可达不会损坏数据**：抓取默认以现有 `out/wiki_builds.json` 为底（只有 `--fresh` 才清空），
失败角色一律保留快照旧数据；若本次 0 个角色成功，会提示改用 `--offline`。
`--offline` 与联网抓取共用同一套解析代码，因此两条路产出的 `wiki_builds.json` / `data.js` 一致。

> 需要单独更新「攻略链接」「套装效果」「来源清单」时，仍可单独调 `fetch_guides.py` /
> `fetch_set_effects.py` / `gen_sources.py`（见下文），它们不参与配装主体重建。

## 抓取门禁与离线重放（`--reparse`）

`fetch_wiki_builds.py` 靠 `STAT_ALIAS`（长句正则扫描）与 `TOKEN_ALIAS`（词条 token 级）
把 wiki 原文里的中文属性名映射成 id。wiki 编辑**大量使用简写**，简写没收录就会**静默**丢词条。

**门禁规则**：每次联网抓取后会自动以同一套别名表 `--reparse` 复核；只要出现**未识别片段**，
脚本**直接以退出码 2 中止**，不写回快照，除非显式加 `--allow-unrecognized`。
所有诊断统一写入 `tools/out/parse_warnings.json`。

```bash
python tools/fetch_wiki_builds.py --reparse --dry   # 预览变更（不写回）
python tools/fetch_wiki_builds.py --reparse         # 离线重放并写回 out/wiki_builds.json
python tools/fetch_wiki_builds.py --reparse --allow-unrecognized   # 明知有片段未覆盖时放行
```

`--reparse` 直接读快照里已保存的 `rows[].reason` **原文**重算，**不联网**，几秒完成；
改别名表 / 分词逻辑后无需重跑 3 分钟的抓取。

> 写 `wiki_builds.json` 必须 `indent=1`（与 fetch 输出一致），否则 diff 会炸成几万行——脚本内已固定。

## 别名表：`STAT_ALIAS` 与 `TOKEN_ALIAS`

两张表分工不同，**别混用**：

| 表 | 生效范围 | 能收什么 | 不能收什么 |
|---|---|---|---|
| `STAT_ALIAS` | 整段长句做正则扫描（`_ALIAS_RE` 按长度倒序，长别名优先） | 全称与不会歧义的异写：`元素精通`、`暴击率`、`生命值`、`充能效率`、`雷伤加成`、`治疗量加成`…… | **不能收短泛词**——`精通` / `暴击` 在描述与 roles 里到处都是，收了会大面积误判 |
| `TOKEN_ALIAS` | 只作用于**已切分好的词条 token**（冒号后面的词条清单，一个 token 就是一个属性名） | 短简写：`精通`→em、`暴击`→cr、`暴击几率`→cr、`生命加成`→hpP、`攻击加成`、`防御加成`、`充能`、`治疗量`…… | 不该出现在词条清单里的词 |

历史 bug（本次已修）：多莉 / 卡齐娜 / 瑶瑶的推荐理由写的是「精通 / 暴击 / 生命加成」，
这三个简写不在任何别名表里 → 被**静默丢弃**，共造成 **7 处副词条缺失**。
修复方式是把简写收入 `TOKEN_ALIAS`（而非 `STAT_ALIAS`，避免长句误判），
并加上「未识别片段上报 + 非空校验」，禁止静默丢词条。

> 改完任一张别名表：`python tools/rebuild_data.py --offline` 即可（或 `--reparse` + `apply` + `build`）。

## 解析回归测试（`test_parse.py`）

守住本次修复的四类问题，防止日后改别名表 / 分词逻辑时回归，**离线运行、不联网**：

```bash
python tools/test_parse.py
```

覆盖四组断言：

- **A. 别名覆盖**：`STAT_ALIAS` 全称映射正确；`TOKEN_ALIAS` 收录 `精通/暴击/生命加成`；
  且断言这些简写**不进** `STAT_ALIAS`（防长句误判）。
- **B. 分词规则**：`/`、空格、`或者` 三种分隔符；`充能效率` 等简写不再落入 unknown。
- **C. 条件词条**：`（仅西风猎弓）`、`（六命可选防御力）` 单独成为 `conditional`，不并入常规推荐；
  说明里另写属性名时，常规取括号外、条件取说明内（`攻击力（六命可选防御力）` → 常规 `atkP` + 条件 `defP`）。
- **D. 产物级断言**：`out/wiki_builds.json` 未识别片段 / 快照空定位为空；7 处历史丢失副词条全部补齐；
  5 组历史空定位全部补齐；`src/data.js` required 死字段 / 空 roles / optional 异常均为 0。

失败项会逐条打印并以非 0 退出码结束，`rebuild_data.py` 检测到即中止，不产出数据。

## 解析完整性诊断（`out/parse_warnings.json`）

`fetch_wiki_builds.py`（含 `--reparse`）每次运行都会刷新该文件，三个数组**都应为空**：

| 字段 | 含义 |
|---|---|
| `unknown` | **未识别片段**：wiki 原文有、别名表覆盖不到、又不像噪音的文本（含 `char` / `row` / `where` / `text`） |
| `empty_roles` | **快照内空定位**：`roles` 推不出且角色级兜底也为空的配装 |
| `no_rows` | **无数据角色**：快照里 `ok=false` 或没有任何配装行的角色 |

出现 `unknown` 时，先补别名表再重跑；确认可忽略时才 `--allow-unrecognized` 放行。

## 数据自检（`check_data.js`）

```bash
node tools/check_data.js
```

扫 `src/data.js` 的 `RAW_CHARS`，结果写 `out/_scan_result.md`，同时打到终端供上层脚本抓取统计行。
除常规字段检查外，还有**派生字段门禁**，以下三项必须为 0、否则退出码非 0：

| 门禁项 | 判据 |
|---|---|
| `required 死字段` | 写了 `subRules.required` 却展开不出任何 ★必选（历史 122 处） |
| `roles（功能定位）为空` | 配装组没有任何功能定位（历史 5 组） |
| `optional（wiki 条件词条）异常` | `optional` 里的 id 非法 / 未落到词条 / 重复 / 未标 opt |

另外报告（**非**门禁）：
`★必选为空的组`（无 ★ 约束，属正常分布）、`optional 未标 opt`、
以及读 `out/parse_warnings.json` 得到的 `未识别片段 / 快照内空定位 / 无数据角色` 三项。

**每次改完数据或升级抓取脚本后跑一次。**

注意：主词条为空**不一定**是 bug——wiki 原文写「空之杯：不强求」时，空就是正确结果
（如欧洛伦 #0 辅助向配装：原文「如果纯当后台、不施放元素爆发，可以什么属性都不堆」）。
判断是否真漏，要回看 `wiki_builds.json` 里的 `reason` 原文。

**副词条直接写 wiki「推荐装备」里的精确值**：每组配装独立携带自己的 `subs`，`SUB_PRESETS` 只用于新建配装时的默认值与「套用预设」。

**功能定位 `roles`**：由 `role_infer.py` 从 wiki 描述前缀推断（`split("主词条")[0]`），
推断不出时退回 `src/data.js` 的 `CHAR_META` 角色级定位兜底，基础词表见 `src/data.js` 的 `BUILD_ROLES`。
注意它与角色级「队伍定位」（主C/副C/辅助）是两回事，别混。

单次调试：`python tools/fetch_wiki_builds.py 胡桃 钟离`（传角色名即只跑这些）。

## 套装简称半自动（`set_short_suggest.py`）

角色卡片上的套装**简称**维护在 `src/data.js` 的 `SET_SHORT`（中文全称 → 中文简称）与
`SET_SHORT_EN`（官方英文名 → 英文简称）：**只收有公认短呼的套装**，没登记的由 `setShortName()`
回落官方全称，所以宁可留空也不臆造。当前两表各 36 条（55 套内置套装余 19 套无简称）。

```bash
python tools/set_short_suggest.py                     # 缺口报告 + 候选 + 可粘贴片段
python tools/set_short_suggest.py --out 简称待确认.md   # 额外写成 Markdown 清单（默认不落盘）
python tools/set_short_suggest.py --backtest          # 拿现有两表回测命中率（附逐条明细）
python tools/set_short_suggest.py --demo              # 拿 3 套假装缺简称，跑通链路
```

- **脚本只读**：不写 `src/data.js`、不 build、不联网。取数优先 `node` + `vm` 载入 `src/data.js`（`SET_EN` 是派生的，纯正则拿不到），node 不可用才回落正则，两条都失败就明确报错退出，绝不静默返回空表。

## 根据定位生成 subRules（离线）

wiki 的追加属性列表没有稳定的必需/同等优先语义，`role_infer.py` 会基于已有的
`roles` 与 `subs` 做保守推断。

```bash
python tools/apply_wiki_builds.py --no-links          # 预览
python tools/apply_wiki_builds.py --apply --no-links  # 写回
```

回写规则：

- `source:'manual'` 或没有 `source` 的旧规则按人工规则保留；
- `source:'heuristic'` 是派生规则，允许后续再次计算；
- **`required` 必须 ⊆ 该配装的 `subs`**：生成端与运行端口径统一，写在 `data.js` 里的每一条
  `required` 都必然能在运行时可标记为 ★必选（历史 bug：旧实现额外做了「required 必须落在
  = 首位核心块内」的**收紧**，把 role 注入的必需项大量清成空数组，造成 122 处死字段）；
- **条件词条 `optional`**：wiki 原文带括号前提的词条（如「暴击率（携带西风剑时）」）由解析层
  单独传入，不计入 `required`/`equal`，只写进 `subRules.optional` 随配装展示；
- 预览报告会统计自动生成的规则组数量与「含条件词条（`subRules.optional`）的规则」组数；
- 写回后运行 `node tools/check_data.js` 和 `node build.js`。

## 临时文件放哪里（规范，2026-10-10 立）

**判据一句话：凡是能重跑生成的东西，都不入库。** `tools/` 既是正式脚本的家，也是一次性脚本与调试产物的家
——靠**命名 + 位置**区分，不要自创路径：

| 类型 | 放哪 | 命名 | 入库 |
|---|---|---|---|
| 一次性 / 调试脚本 | `tools/` | `_<用途>.py` / `.js` / `.mjs` | ❌ `.gitignore` 的 `tools/_*` |
| 临时产物：截图 / 报告 / 量测脚本 | `out/_tmp/<YYYYMMDD>-<用途>/` | 沿用 `_` 前缀 | ❌ |
| 大体积中间素材（攻略图批次等） | `out/<素材名>/` | 如 `guide_subtiers/`、`main_c/` | ❌ 默认；要入库须加 `!` 例外 |
| 抓取缓存 | `out/<名字>_cache/` | `cache/`、`guides_cache/` | ❌ `*cache*` |
| 正式产物（重跑贵、有参考价值） | `out/<名字>.json` / `.md` | **不带**下划线 | ✅ 且在白名单里 |

五条硬规则：

1. **`_` 前缀 = 本地自用，永不 `git add`。** 过去这只是软约定，多次被误提交后又 `git rm --cached` 摘除
   （`_commit_persist_test.js` / `_no_heuristic_required.js` / `_recompute_roles.py` / `_strip_heuristic_required.js`
   都踩过）；现在 `.gitignore` 的 `tools/_*` 强制兜住，脚本可以放心写。
2. **脚本不要在仓库里造垃圾目录。** CDP / Playwright 的 `user-data-dir` 必须指向系统临时目录
   （Python `tempfile.mkdtemp()`、Node `os.tmpdir()`），**不许落在 `tools/` 或 `out/`**。
   2026-10-10 已清理历史遗留的 17 个 `.chrome-x*` 目录（约 1.1 GB）。`.gitignore` 里的 `.chrome-*/` 是兜底，不是许可。
3. **产物统一落 `out/`，不散在 `tools/` 根。** CDP 截图这类已散落的，归档到 `out/_tmp/<日期>-<用途>/`
   （如 `out/_tmp/cdp-20261009/`）。
4. **`out/` 是白名单制**：`tools/out/*` 默认全忽略，只有 8 个正式快照用 `!` 放行
   （`guides.json` / `wiki_builds.json` / `set_effects.json` / `parse_warnings.json` / `sets_warnings.json` /
   `report.md` / `sources.md` / `sources.html`）。新增入库产物先过两问：别人 checkout 下来用得上吗？重跑很贵吗？
5. **提交前必查 `git status --short`**：不应有任何 `??`，也不应有任何 `_` 前缀条目。

> 大体积素材（`out/guide_subtiers/` 约 943 MB、`out/guides_cache/` 约 821 MB）**不入库但保留在本地**：
> 校准结论已写进本文档，图本身只在需要人工复核时才读。

## 回写格式的坑

`apply_wiki_builds.py` 重建条目时，`items[1]/src/note` 都带着原文前导空格，
用 `", "` 拼接会各多出 1 个空格 → 全表 diff。代码里已用「记住原 pad 再还原」处理，
`--apply` 后 `git diff src/data.js` 应**只有真正变了的字段**。
