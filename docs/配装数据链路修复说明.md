# 配装数据链路修复说明

> 本文档记录 2026-09-18 对「wiki 原文 → `tools/out/wiki_builds.json` 快照 → `src/data.js` 内置数据 → `index.html`」
> 这条**角色配装数据生成链路**的修复内容与前后对照。
> 起因与逐字段证据见同目录 [`配装数据核对报告.md`](配装数据核对报告.md)；
> 工具用法见 [`../tools/README.md`](../tools/README.md)，整体设计见 [`DESIGN.md`](DESIGN.md)。

## 0. 一句话结论

修复后，**只运行 `tools/` 里的脚本**即可重建正确数据：联网抓取走 `rebuild_data.py`，
wiki 不可达时走 `rebuild_data.py --offline`（基于既有 `tools/out/wiki_builds.json` 快照重放），
两条路共用同一套解析代码，产出一致。核对报告点名的五类问题**全部清零**。

修复前 / 后关键指标：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 副词条静默丢失 | **7 处** | **0** |
| `required` 死字段（写了 required 却展开不出 ★） | **122 组**（34.7%） | **0** |
| `roles`（功能定位）为空的配装组 | **5 组** | **0** |
| 未识别片段（wiki 原文有、解析层丢弃） | **7 段** | **0** |
| 条件词条（wiki 括号前提）结构化为 `optional` | 0（被当常规推荐） | **24 组 / 53 条** |
| `out/parse_warnings.json` 三项清单（未识别 / 空定位 / 无数据角色） | 有内容 | **全空** |

> 唯一仍被 `check_data.js` 报出的「空主词条」是**欧洛伦 #0 空之杯**，
> 属 wiki 原文「不强求」，**非缺陷**，详见 §5。

## 1. 问题来源

核对报告对四层链路逐层比对后给出的定性：

| 层级 | 修复前结论 |
|---|---|
| 快照 → 内置数据（`apply_wiki_builds.py` 回写） | **一致**：352 组全字段 0 差异，回写环节无损 |
| wiki 原文 → 快照（`fetch_wiki_builds.py` 解析） | **有损**：7 处副词条被**静默**丢弃（别名未覆盖） |
| 派生字段 `subRules` | **不可信**：122 组 `required` 被运行时清零，82.4% 的组最终没有 ★必选 |
| 配装本体（套装 / 主词条 / 副词条 / 定位） | 大体正确，但有 5 组定位为空、条件词条被当常规推荐 |

即：**缺陷集中在解析层与派生字段推导层**，回写层是忠实的。修复因此聚焦于
`fetch_wiki_builds.py`、`role_infer.py`、`apply_wiki_builds.py` 与运行端 `src/data.js` / `src/app.js`。

## 2. 修复项清单（逐条）

### P0-1　补全词条别名词表，消除静默丢词条

**问题**：解析层用 `STAT_ALIAS` 把中文属性名映射成 id，未收录的写法被**静默丢弃**。
wiki 副词条里写的是简写「精通」「暴击」「生命加成」，三个都不在表里 →
多莉 / 卡齐娜 / 瑶瑶共 7 处副词条丢失。

**修复**：`fetch_wiki_builds.py` 引入 **两张分工明确的别名表**：

- `STAT_ALIAS`：在**整段长句**上做正则扫描（`_ALIAS_RE` 按长度倒序，长别名优先），
  只收**不会歧义**的全称与异写（`元素精通`、`暴击率`、`生命值`、`充能效率`、`雷伤加成`、`治疗量加成`……）；
- `TOKEN_ALIAS`：**新增**，只作用于**已切分好的词条 token**（冒号后清单，一个 token 即一个属性名），
  因此可以安全收录简写：`精通`→em、`暴击`→cr、`暴击几率`→cr、`生命加成`→hpP、
  `攻击加成`→atkP、`防御加成`→defP、`充能`→er、`治疗量`→heal 等。

为什么不把「精通」「暴击」直接塞进 `STAT_ALIAS`：这两个词在推荐理由与 roles 描述里**到处都是**，
长句扫描会大面积误判。按语境分表后，简写只可能出现在词条位，误判风险归零。

### P0-2　未识别片段上报 + 抓取门禁（禁止静默丢弃）

**问题**：解析不到的词条此前**默默丢掉**，不报错、不记录，缺陷只能靠人工逐段反查原文才发现。

**修复**：
- `parse_fields()` 除了返回 `mains / subs / conditional`，还返回 **`unknown`（未识别片段）**，
  并用 `NOISE_TOKENS` 白名单（`不强求`、`推荐`、`无`、`-` 等非属性噪音词）过滤误报；
- 每次 `--reparse`（含联网抓取后的自动复核）把诊断写入 **`tools/out/parse_warnings.json`**，
  含 `unknown` / `empty_roles`（快照内空定位）/ `no_rows`（无数据角色）三个清单；
- **抓取门禁**：只要 `unknown` 非空，脚本**直接以退出码 2 中止**、不写回快照，
  除非显式 `--allow-unrecognized` 放行。

效果：以后 wiki 一旦出现别名表未覆盖的新写法，会**当场拦下**而不是悄悄丢数据。

### P0-3　移除 `required` 收紧逻辑，消除 122 处死字段

**问题**：`role_infer.py` 按角色定位推导 `required`（如「精通」定位 → `required:['em']`），
但旧实现额外做了一次「**required 必须落在 `=` 首位核心块内**」的**收紧**，
把注入的必需项大量清成空数组，于是 `src/data.js` 里留下 `required:['em']` 这类
**永远不可能生效的死字段**（122 组，占 34.7%）。

**修复**：生成端与运行端**口径统一**为「`required` ⊆ 该配装的 `subs`」：

- `role_infer.infer_subrules(roles, subs, optional)`：去掉核心块收紧，只按定位往 `subs` 里已存在的词条加 `required`；
- `src/data.js` 的 `subIdsToSubs()`：同步移除运行时的前缀块收紧逻辑；
- 结果：写在 `data.js` 里的每一条 `required` 都必然能在运行时可标记为 ★必选，死字段归零。

> ★必选为空仍会有 168 组——它们本就是「无 ★ 约束」的配装（wiki 未表达必需语义），
> 属**正常分布**，不是缺陷；门禁只查「写了 required 却展开不出 ★」。

### P1-1　条件词条结构化为 `optional`，不再混入常规推荐

**问题**：wiki 原文用括号写前提（`暴击率（仅西风猎弓）`、`防御力（六命可选防御力）`、
`（携带西风剑时）`、`（用以触发西风大剑特效）`），旧解析**无差别并入常规推荐**，
把「搭配西风武器才堆」的暴击率当成人人都要的无条件词条。

**修复**：
- `fetch_wiki_builds.py` 用 `COND_CLUES`（`西风`/`命`/`可选`/`携带`/`触发`/`特效`/`限定`…）
  识别括号条件，结构化输出 `conditional: [{where, stat, note}]`；
  括号里只是流派出处的（`（输出）`/`（辅助）`）按 `VARIANT_MARKS` 当常规词条处理；
  说明里另写属性名时取「说明里那个」——`攻击力（六命可选防御力）` → 常规 `atkP` + 条件 `defP`；
- `apply_wiki_builds.py` 的 `optional_subs()` 把条件词条汇总进 **`subRules.optional`** 落库；
- `src/data.js` 的 `subIdsToSubs()` 支持 `optional`：标记 `opt`，并可把「没进常规 subs、
  只在原文里以条件形式出现」的词条补进词条列表；
- `src/app.js` 在配装卡片上以「**◇ 条件词条**」单独展示，并带 tooltip 说明
  「这些词条只在原文给定的前提下才需要，例如搭配了对应武器或解锁了命座」。

### P1-2　补齐 5 组空 `roles`（角色级定位兜底）

**问题**：闲云 #1、云堇 #0、云堇 #1、伊涅芙 #2、莉奈娅 #1 五组配装的推荐理由**只描述套装效果**，
不含任何定位关键词，`infer_roles()` 推不出定位 → `roles=[]`，会连带让 `subRules` 失真。

**修复**：`role_infer.py` 新增 `load_char_roles()`，从 `src/data.js` 的 `CHAR_META`
读角色级基础定位（`maindps`/`subdps`/`support` → `输出`/`副C`/`辅助`）。
当描述文本 + 主副词条都推不出定位时，**退回角色级定位兜底**，保证每组至少有 1 个定位。

### P2-1　统一分词规则 + 建立解析回归测试

**问题**：`reason` 分隔符不统一（`/`、空格、`或者`、`（输出）/（辅助）` 双版本混写），
靠启发式兜住，是丢词条的温床，且无测试守护。

**修复**：解析层统一处理多分隔符与变体后缀；新增 **`tools/test_parse.py`**：
36 条断言覆盖「别名覆盖 / 分词规则 / 条件词条 / 产物级断言」四组，
失败即非 0 退出（`rebuild_data.py` 检测到会中止，不产出坏数据）。

### P2-2　快照重放 + 一键重建入口（wiki 不可达也能重建）

**问题**：旧流程「抓取 → 回写」强依赖联网，wiki 挂掉或超时就会把快照洗成残缺版；
改一次别名表要重跑 3 分钟抓取。

**修复**：
- `fetch_wiki_builds.py`：**默认以现有 `wiki_builds.json` 为底**（仅 `--fresh` 清空），
  失败角色保留快照旧数据；抓完自动跑一次 `--reparse` 复核；
  `--reparse` 直接读快照里 `rows[].reason` **原文**离线重算，不联网、几秒完成，
  与联网抓取共用同一套 `parse_fields`；
- 新增 **`tools/rebuild_data.py`** 作为唯一入口：抓取（或 `--offline` 重放）→ 回写 →
  `test_parse.py` → `check_data.js` → `node build.js`，串成一条链，任一步失败即中止；
- 支持 `--offline` / `--dry` / `--no-build` / `--allow-unrecognized` / 指定角色。

### P2-3　扩展 `check_data.js` 自检门禁

`check_data.js` 在原有字段检查外，复刻运行端展开逻辑，新增三项**硬门禁**（非 0 即退出码非 0）：

| 门禁项 | 判据 |
|---|---|
| `required 死字段` | 写了 `subRules.required` 却展开不出任何 ★必选 |
| `roles（功能定位）为空` | 配装组无任何功能定位 |
| `optional（wiki 条件词条）异常` | `optional` 的 id 非法 / 未落到词条 / 重复 / 未标 opt |

另外汇总读 `out/parse_warnings.json` 的「未识别片段 / 快照内空定位 / 无数据角色」三项。

## 5. 非缺陷项：欧洛伦 #0 空之杯为空

`check_data.js` 仍会列出 `欧洛伦 #0 [烬城勇者绘卷] goblet=<空>`，这是**正确结果，不是缺陷**。

wiki 原文（`out/wiki_builds.json` → `欧洛伦.rows[0].reason`）：

> 辅助向配装方案，需要施放元素爆发就堆叠充能，搭配【西风猎弓】就堆暴击率，
> 如果纯当后台、不施放元素爆发，可以什么属性都不堆。确保凑齐该套装的4件套是最首要的。
> ……主词条时之沙：充能效率　空之杯：**不强求**　理之冠：暴击率（仅西风猎弓）……

原文明确写「空之杯：**不强求**」，因此 `goblet` 解析为 `[]` 是忠实还原。
该组的「搭配西风猎弓才堆暴击率」这一条件已正确结构化为
`conditional: [{circlet, cr, 仅西风猎弓}, {subs, cr, 仅西风猎弓}]`，并在前端以「◇ 条件词条」提示。

## 6. 复现与日常维护

```bash
# 联网重建（推荐日常入口）
python tools/rebuild_data.py

# wiki 不可达 / 想快速重放：基于既有快照离线重建
python tools/rebuild_data.py --offline

# 只改了别名表或分词逻辑
python tools/rebuild_data.py --offline

# 只预览不落盘
python tools/rebuild_data.py --dry

# 只重建部分角色（联网时生效）
python tools/rebuild_data.py 胡桃 钟离

# 明知有片段未覆盖、需强行落盘
python tools/rebuild_data.py --allow-unrecognized
```

任一路径结束后会自动跑 `test_parse.py`、`check_data.js` 与 `build.js`，
门禁（死字段 / 空 roles / optional 异常 / 未识别片段）非 0 即中止，保证不产出坏数据。

## 7. 残余事项（不属本次缺陷，供后续参考）

1. **快照时效**：`out/wiki_builds.json` 抓取于 2026-09-14，若 wiki 期间有修订，
   数据不会自动跟进；需要时会话内跑一次 `python tools/rebuild_data.py` 即可刷新。
2. **作者攻略正文未读取**：词条挂的米游社图文攻略本项目从不解析（一图流），
   仅作为来源链接列出，因此只核到「链接 / 作者」层面。
3. **★必选为空 168 组**：wiki 本身无「必需」语义，这批组没有 ★ 约束属正常分布，
   由用户在编辑器里按需手填或由定位推断补充。

### 语义（对齐实际玩法）

- `sets` 是**套装候选池**（池内不写重复同名套装）：**1 个 = 4 件套；≥2 个 = 2+2 任选两套散搭**。
  选哪两套是玩家的事，数据层**只给候选池，不替玩家定组合**。
- `need: 4` 表示**池内任选其中一套穿满 4 件**（如林尼「流浪大地的乐团 / 沙上楼阁史话」），与 2+2 池区分开。
