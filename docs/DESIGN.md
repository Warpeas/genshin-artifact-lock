## 1. 要解决的问题

圣遗物背包越堆越多，真正难的从来不是「这件好不好」，而是三件连在一起的事：

1. **留什么** —— 一个「绝缘套·充能沙」，我该留充能沙还是攻击沙？
2. **留几件** —— 养了 6 个角色，难道要留 6 件充能沙？
3. **能不能喂** —— 哪些套装我压根用不上，可以整套清掉？

这三问单独看都不难，难在**必须跨全部角色一起算**。人工做法是逐个角色查攻略再心算汇总，角色一多就必然出错、也必然过时。

### 本工具的核心抽象

把问题形式化成一个**三维汇总**：

```
套装 × 部位 × 主要属性  →  要不要留 / 留几件 / 给谁用
```

每个角色贡献若干条需求（配装组 + 各部位可接受的主要属性 + 优先级），汇总引擎把所有启用角色的需求**叠加**进「套装 × 部位 × 主要属性」的格子里，一次性输出完整清单。

### 最终产出物

不是一张表，而是**可以直接照抄进游戏的锁定方案**：

- 每个套装一组「游戏内锁定方案候选」，按追加属性需求聚类生成，**候选数量不限**；
- 由你用「并入 / 采纳」收敛到游戏内每套 3 个预设以内；
- 另有可选的「详细件数」视图，回答留几件、给谁用。

> 设计上刻意**不做**「自动压到 3 套」——理由见 §7.1。

## 2. 整体架构

### 2.1 单文件构建

```
src/data.js  (数据)  ┐
src/app.js   (逻辑)  ├─ node build.js ─→ index.html （单文件，CSS/JS 全内联）
src/styles.css(样式) │
src/template.html(骨架)┘
```

- **运行时零依赖、零网络**。产物 `index.html` 双击即用，可随便拷贝、发给别人。
- 源码四件套分离，是为了让改数据和改逻辑都能被 review；**构建产物不入库修改**（改了下次 build 会被覆盖）。
- 构建时做两道保护：源码禁止出现 `</script`；内联后校验关键签名存在。

选择单文件的代价是 `index.html` 有 350KB+ 量级、且必须走构建；收益是**分发成本为零**（GitHub Pages 直接托管，用户不需要任何工具链）。这个项目的使用场景是「玩家打开网页用一下」，分发成本远比工程优雅重要。

### 2.2 运行时结构

| 层 | 职责 |
|---|---|
| `data.js` | 内置数据：套装 / 角色 / 属性库 / 枚举 / 版本与 CHANGELOG |
| `app.js` | 汇总引擎、聚类合并、四个页面交互、i18n、存档与迁移 |
| `styles.css` | 样式，含打印与 ≤560px 手机端适配 |

状态存 `localStorage`（key `genshin_artifact_lock_v1`），**不联网、不上传**。已读公告用独立 key，避免「恢复内置默认库」时把已读状态一起清掉。

### 2.3 中英文显示

界面语言和数据语言在状态上分开保存，顶栏按钮默认同时切换二者；翻译采用内置词典、官方英文数据名和少量动态句式规则，不依赖网络服务。英文文案由 AI 生成，尚未经过完整人工校对，也没有覆盖所有界面，因此英文模式会明确提示这一限制；未收录的内容保留中文，避免生成不可靠的半成品翻译。

备份采用用户数据格式而不是整份运行时状态：导出自定义角色 / 套装、对内置角色 / 套装的修改、方案整理、用户规则和界面偏好；系统内置角色与套装库不写入备份。导入时先保留当前版本的系统库，再把备份中的用户数据合并进去，因此升级系统数据后仍可恢复旧的个人配置。

套装管理中的 2 件套和 4 件套效果都属于用户可编辑字段，修改后立即保存；新增自定义套装通过弹窗填写后插入列表首位。列表提供「恢复内置顺序」，把自定义套装集中放在前面，再按 `SETS` 的系统顺序排列内置套装；「恢复全部内置套装显示」只负责取消内置套装的隐藏状态。

每套的 2 / 4 件套定位也在这里编辑，**按件套分块**（`posBlockHtml()`：一块 = 一个件套，块内「大类」「关键词」相邻两行；`.sm-roles` 为双列，≤999px 转单列）：大类行恒为 `BUILD_CATS` 4 项（输出 / 辅助 / 生存 / 功能），关键词行取 `BUILD_KWS` 22 项 + 该层已有的额外取值。块头「内置 / 已修改」徽标（`factoryPosOf()` 出厂定位 + `posPartDirty()` 逐件套比对）与 ↺ 重置只作用于该件套，块底另可「全部重置为内置」，重置目标恒为图鉴出厂值；自定义套装没有出厂基线，不显示徽标与重置入口。芯片只保留「金色 = 已选 / 普通 = 未选」两态——「是不是内置项、改没改过」由块头徽标统一表达，不再用第二套色谱。历史存档里被写进大类层的关键词由 `splitPosLayers()` 在 `normalize()` 末尾归位到同件套的关键词层（反向亦然，排序去重、不丢已选值），且该清洗排在工厂值回填之后，不会被回填覆盖。

套装名有两套写法：**角色卡片**上用 2 字简称（内置表 `SET_SHORT` / `SET_SHORT_EN`，只收有公认短呼的套装，缺省回落官方全称；用户在套装管理里填的简称优先），**方案页 / 评分表 / 编辑页 / 导出与复制**一律用官方全称——简称只是卡片上的省位写法，任何会写进锁定方案或导出文本的地方都保持全称，避免与游戏内锁定界面（中文全称）对不上。用户改的简称只落在用户数据层，内置表不被用户操作改写。

## 3. 数据模型

### 3.1 角色 → 配装组 → 需求

```
角色 (127)
 ├─ 元素 / 国度 / 队伍定位(主C·副C·辅助) / 备注 / 攻略来源
 └─ 配装组[]           ← 第 0 组是「主推」，其余备选
      ├─ sets     套装候选池[]（1 个 = 4 件套；≥2 个 = 2+2「任选两套散搭」）
      ├─ need     可选形态标注：4 = 池内任选一套穿满 4 件；2 / 缺省 = 池内任选两套（2+2）
      ├─ sands / goblet / circlet   各部位主词条[]，按优先级降序
      ├─ subs     追加属性[]（来自 wiki 精确值）
      ├─ subRules 追加属性语义层（人工或定位启发式生成）
      └─ roles    配装功能定位[]（两层：大类 输出 / 辅助 / 生存 / 功能 + 关键词 增伤 / 减抗 / 治疗 / …）
```

两组易混淆的「定位」，务必分清：

| | 层级 | 取值 | 用途 |
|---|---|---|---|
| **队伍定位** | 角色级 | 主C / 副C / 辅助 | 筛选、分组、聚合 |
| **功能定位** | 配装级 | 大类 `BUILD_CATS`：输出 / 辅助 / 生存 / 功能（4 项，必选、可多选）<br>关键词 `BUILD_KWS`：增伤 / 剧变反应 / …（22 项，可选、可多选，可跨大类） | 描述「这套配装拿来干嘛」，在**套装管理里按件套（2 / 4）分层编辑**：大类一行恒 4 项，关键词一行；`roles` 字段按 `pos2 / pos2kw / pos4 / pos4kw` 落库，由套装派生的配装定位取「大类｜关键词」合成展示 |

### 3.2 追加属性：排序 + 必选 + 重要度算子

追加属性用**有序数组 + `=` / `>` 算子 + ★必选**表达：

```js
[{ id:'cr',  req:true, op:'>' },   // 第 1 条最想要（1.0）
 { id:'cd',  req:true, op:'=' },   // = 与上一条同重要
 { id:'atkP',         op:'>' }]    // > 比上一条更低（×0.72）
```

**设计理由**：`=` / `>` 把「同重要 / 次重要」**显式表达**出来，而不是依赖隐含的位置序号——「双暴同重要」这种最常见的关系能被稳定表达，用户也不需要填有意义的数值。

由此还得到一个关键红利：**「重要属性块」可以直接从数据读出来**——从第 1 条起沿 `op='='` 延伸的前缀块，再并入所有 ★必选。不需要任何魔法阈值（见 §5.3）。

#### 3.2.1 原始顺序与语义规则分离

wiki 的 `subs` 是推荐表中解析出的原始顺序，但通常没有明确说明哪条是「必需」或哪几条同等重要。为避免把数组第一项误当成必需，内置数据把解释层单独放在 `subRules`：

```js
subRules: {
  required: ['em'],
  equal: [['cr', 'cd']],
  optional: [['er', '少量充能效率，用于优化大招循环']],
  source: 'heuristic',
}
```

`data.js` 展开默认角色时，把它编译成现有运行时结构：`required` 变成 `req:true`，`equal` 中排序靠后的词条变成 `op:'='`，`optional` 里点名的词条标 `opt:true` 并把第二元素存进 `optNote`（悬停 ◇ 时显示的前置理由）。`optional` 支持两种写法：旧的 `['cr']` 纯字符串（无理由，悬停回退通用说明）与 `[['cr','携带西风秘典时']]` 元组；**不在 `subs` 里的 optional 会被补到池末尾并标 ◇**，避免这类词条凭空消失。`source:'manual'` 是人工校准锚点，数据回写和出厂同步不得覆盖；`source:'heuristic'` 是可重复计算的派生结果。**注意**：新建 `subRules` 时 `source` 只能写 `manual`——`tools/apply_wiki_builds.py` 只保护这一种取值不被重跑覆盖，写别的值下次 `rebuild_data.py` 会把它重算掉。

#### 3.2.2 定位启发式的边界

`tools/role_infer.py` 只使用本地 `roles` 与 `subs` 生成规则，不访问网络：

- 同时存在 `cr` / `cd` 时生成 `equal: [['cr', 'cd']]`，但不会把双暴自动标成必需；
- `精通`、`增幅反应`、`剧变反应` 定位在存在 `em` 时要求 `em`；
- `充能` 定位在存在 `er` 时要求 `er`；
- `治疗` / `护盾` 定位只在对应生命或防御词条存在时加入必需项。

这是一层保守的自动填补，不等价于攻略原文中的确定结论。人工调整时使用 `source:'manual'`，后续离线回写会优先保留。

### 3.3 三个锚点：让「还原」和「自动跟随」都能落地

| 锚点 | 是什么 | 解决什么 |
|---|---|---|
| `bkey` | `角色名#序号` 的出厂指纹 | 还原的判定锚点，**用户改名后照样能还原** |
| `fcanon` | 配装组内容指纹 | 「内置数据自动跟随」：指纹未变说明用户没改过 → 用新出厂覆盖；改过则一律不动 |
| `skey` | 出厂名 | 存档兼容 |

这套设计解决的是一个真实矛盾：**既要让内置数据随版本自动更新，又绝不能覆盖用户的手工修改**。判定标准必须是「你到底改没改」，而不是「版本号大小」。

配套的三层还原粒度（只还原主推 / 还原单组 / 还原整角色）也是为此——用户改坏的程度不同，需要的回退粒度也不同。

### 3.4 编辑保存边界：角色即时生效，配装显式保存

角色编辑浮窗采用「基础信息即时同步 + 配装草稿隔离」的边界：

- 角色名称、元素、国度、队伍定位、备注和攻略来源，修改后立即写入 `localStorage`，不依赖底部按钮；新建角色填写名称后立即建立记录。
- 配装编辑是第二层浮窗，使用独立的 `bmDraft` 深拷贝；套装、主推状态、主要属性、追加属性和功能定位只有点击「保存」才写回角色草稿，取消 / 关闭 / 点击浮窗外会放弃未保存改动。
- 角色编辑浮窗的「保存配装修改」只负责把已经在配装浮窗中保存的配装草稿写回角色；「关闭」不会撤销已经即时保存的角色基础信息。

这样既避免角色名称等基础信息因误关闭而丢失，也保留配装编辑过程中的撤销能力，防止试排词条时污染现有方案。

属性添加采用低打断的编辑方式：点击「添加主要属性」或「添加追加属性」时，直接从对应属性库顺序中取第一个尚未使用的属性，随后由用户在行内下拉框调整。这样新增动作只有一个确定结果，不需要再打开第三层选择浮窗，同时仍通过重复校验保证同一列表不会出现重复属性。

## 4. 汇总引擎

### 4.1 权重模型

```
得分 = 配装优先级 × 件套形态 × 主要属性优先级     （跨角色累加）
```

| 维度 | 取值 | 权重 |
|---|---|---|
| 配装优先级 | 主推 / 备选 | 1.0 / 0.55 |
| 件套形态 | 4 件套 / 2+2 任选 | 1.0 / 0.8 |
| 候选池折减 | 池内每套 ×`min(挑取套数, 池宽) ÷ 池宽` | 2 套池 ×1.0、3 套池 ×0.67、4 套池 ×0.5；2+2 池另有 0.45 权重下限（略高于过渡阈值 0.4，保证池内每套的词条需求都进锁定方案） |
| 主要属性优先级 | 第 1 条最优；其后 `=` 同权 / `>` 降权 ×0.72 | 1.0 / 1.0 / 0.72 … |

### 4.2 分级与保留件数

| 得分 | 分级 | 含义 |
|---|---|---|
| ≥ 0.8 | **必留** | 有角色把它当最优解，至少留 1 件 |
| 0.4 – 0.8 | **过渡** | 只有次选或备选配装需要，有就用、不专门刷 |
| < 0.4 | 不显示 | 需求太弱，视为狗粮 |

保留件数：沙/杯/冠 = 以该词条为**最优解**的角色数（同角色多套配装不重复计数），区间 1–4；花/羽主属性固定，件数 = 需要该套装的角色数。

> **暴击率冠与暴击伤害冠自动合并**为「二选一」——它们实际可互换，分开统计会严重高估（实测把 12+3 件修正为 7 件）。这类「看起来是两个格子、实际是一个需求」的合并，是让输出可用的关键细节。

## 5. 游戏内锁定方案的生成

这是本项目最核心也最花心思的部分。**目标不是"算出一个最优解"，而是"生成能直接照抄进游戏的方案，且不存伪"。**

### 5.1 为什么不自动压到 3 套

游戏内每种套装**至多 3 个自定义方案**。最直觉的做法是自动压缩到 3 个——但这是错的：

> 攻略明确指出，**需求差异大的角色不宜并入同一方案，否则会「存伪」**——把别的角色用不上的圣遗物也锁进来。

「压到 3 套」和「不存伪」在需求多样时**直接冲突**。强行压缩必然产生伪锁定，而伪锁定正是用户最初要解决的问题。

所以设计是：**给出全部候选 + 手动整理**。工具负责生成正确的候选并保证合并判据可靠，收敛与否、怎么收敛由你决定（采纳数超 3 时页面顶部给提醒，但不替你拍板）。

### 5.2 候选生成流程

1. **角色分组**（凝聚聚类，见 §5.3）
2. **候选合成**：每组生成一份候选——**全方案唯一一份追加属性条件**，主要属性逐部位按「票数 × 重要度」降序取到累计覆盖 ≥ 70%，上限 3 个
3. **散件/过渡规则同权加入**：如「元素伤害杯」这类与具体角色无关的稀有件，每条启用规则转成一份候选，**与角色聚类候选同权**参与并入/采纳，不单独占槽位
4. **手动整理**：「并入…」合并、「采纳」勾选、「拆回」还原
5. **导出**：只导出已采纳方案，格式与页面一致

### 5.3 合并判据：看「重要属性」，不看相似度阈值

判据与排序是**两件事**，刻意分开：

- **能不能合**，先看双方高优先追加属性：取前两条并沿 `=` 扩展，再并入 ★必需；要求两边核心有足够重合。
- 双方普通需求都不超过 3 条、需求集合完全相同、且没有人工校准规则时，忽略列表排列差异，直接视为兼容。该例外不适用于长列表，也不因「长列表包含短列表需求」而触发。
- 人工校准规则优先于短列表顺序豁免。条件词条不进入自动合并高优先集合，但仍按原规则参与候选池与展示。
- **整组兼容采用完整链接**：两个组只有在所有跨组角色对都直接兼容时才能合并，避免 A 与 B、B 与 C 相似就把不兼容的 A 与 C 传递并组。合并过程不再用不断收缩的核心交集作为后续判据。
- **先合谁**，取决于组间所有跨组角色对的最低追加属性余弦相似度；分数相同按稳定需求签名打破平局。候选软上限不再通过绕过兼容判据来强行合并。

这样分工很清晰：**判据管「能不能合」，相似度管「先合谁」**——既保留「按追加属性需求合并」的语义，又不会被次要属性干扰。

**全量内置数据回归（2026-10-09）**：按实际套装使用角色重算 55 套、共 128 个锁定方案候选；所有组均保留成员的沙 / 杯 / 冠 rank1 主属性、前 5 条追加属性需求、★必需标记与◇条件词条，角色输入顺序反转后分组不变。尼可与布伦妮在「天之美赐」下归入同一方案。

大组仍可能合理出现，不能只凭人数判为误合并。例如「战狂」最大组 44 人，共同需要暴击率 / 暴击伤害，追加属性池 7 条；攻击力% 有 38 / 44 人需要，推荐命中 3 条。少数角色的差异需求保留在同一池中，由方案内角色偏好分组区分。该结果是可接受的宽池，不代表每件胚子都适合组内所有角色；如后续用户反馈照抄不便，应优先评估支持度阈值与偏好展示，而非仅按组人数拆分。

### 5.4 主属性：逐部位独立合并

主要属性**不参与相似度计算**，而是逐部位独立合并——因为「合并是按追加属性要求类似，单独每个部位合并主要属性要求」。

合并口径分两层，`rank1`（组内任一角色的头号主属性）**先全部保底**，其余条目再补足：

1. **`rank1` 保底**：组内任何角色的头号主属性一律保留，**不参与** `MAIN_COVER` / `MAIN_MAX` 截断。理由：rank1 是该角色配该部位的**唯一正确解**，丢一个就等于该角色的件全漏锁——这是硬缺陷；而次要主属性丢失只是条件收窄，属可接受。
2. **次要主属性补足**：其余条目按「票数 × 重要度」降序，取到累计覆盖 ≥ 70%（`MAIN_COVER`）或总条数达 3 个（`MAIN_MAX`）为止。上限存在的意义是：条件过宽就会「存伪」。

因此单部位主属性**实际条数可能多于 3 条**（`MAIN_MAX` 只约束次要条目），上限等于「该部位 `rank1` 的去重个数」。实测全量 45 套装中有 24 个部位超过 3 条，最多 9 条（`昔日宗室之仪 · 空之杯`，18 人组）。

排序是**确定性**的：计票 `score = Σ(票数 × 优先级权重)` 降序，同分按 `MAIN_STATS[slot]` 的声明序 tiebreak；两者都只依赖成员**集合**，与角色在数据里的先后顺序无关（`mainTally` / `mainStatOrder` / `mainRanked` 均为纯函数）。

方案级「并入…」（`mergePlans`）同口径：先并入全部 `rank1` 保底，再补齐到 `MAIN_MAX` 后截断，避免越并越宽、最后宽到等于「不限」。

### 5.5 追加属性池与 ★

- 池 = 组内任一角色前 `SUB_POOL_TOP`（5）条需求的**并集**。**池宽 = 合并结果本身，不再收口**——旧实现按 `SUB_POOL_MAX = 5` 收口，既会丢掉池尾条目，也会把排在池尾的 ★ 一起截断。
- ★必需（`SUB_REQ_MAX = 4`）取的是「组内**任一**角色标了必选」的**并集**，按「标它的人数 → 名次权重」排序后**截到 4 条**，并**置于池首**（`unshift`，与 `fuseSub` 同口径）。
  - ★ 只是**标记语义**——「这条是某人明确点名要的」。是否真在游戏里设成「必须」由用户按重要程度决定，工具不替他决定，所以既不取交集（那会漏掉真正需要的词条）也不无限放宽（最多 4 条，与圣遗物最终 4 条追加属性对齐）。
- **◇条件词条**（wiki「携带西风剑时才堆」类推荐）强制进池，低优先但始终可见。
- 池宽取消上限后不再需要「按次要偏好小队补池」的保底逻辑——池尾不再被切掉，★ 与条件词条恒在池内。

### 5.6 命中条数

- **系统推荐值**（`N_rec`）：统计池里支持度 ≥ `SUB_MIN_HIT_SUPPORT`（50%）的条目数，钳到 `SUB_MIN_HIT_MIN`（2）～`SUB_MIN_HIT_RECOMMEND_MAX`（3），再取实际生效 `N = min(N_rec, 池宽, SUB_MIN_HIT_MAX = 4)`。
- UI 文案为「**推荐至少 N 条**」，方案卡片上**只读展示**该推荐值——它就是最终值，不再有 1–4 的下拉修改入口（想更严 / 更松请在游戏内锁定界面自行调整）；历史存档里旧的手动覆盖值由 `applyMinHit` 忽略。
- 散件 / 过渡规则方案没有角色组、算不出支持度，取推荐值下限 2 条；手动「并入…」同理（等于重新起一套）。
- 「仅有 3 条追加属性的圣遗物所需数量自动减 1」属**游戏侧行为**：本工具只输出建议过滤条件，不模拟、不承诺件数。

## 6. 与游戏内规则的对齐

| 游戏内规则 | 本工具的处理 |
|---|---|
| 每套至多 3 个自定义方案 | 候选不限，由你收敛到 3 个以内；超出时提醒但不代劳 |
| 沙/杯/冠可设主要属性与追加属性；花/羽主属性固定 | 完全一致，花/羽只参与追加属性；方案与导出文本里把这两个部位的主属性**写出具体值**（「生命值（固定）」/「攻击力（固定）」），照抄时无须回头确认 |
| ★必须 = 没有就不锁 | 仅作**标记语义**（组内任一人标了即保留），上限 4 条、置于池首；是否真按「必须」用由你定 |
| 命中条数 | 系统按组内支持度**推荐**「至少 N 条」（N_rec = clamp(过半支持度条目数, 2, 3)，N = min(N_rec, 池宽, 4)）；该值**即最终值**，页面只读展示、不提供 1–4 修改入口（需更细 / 更宽请在游戏内调整） |
| 追加属性顺序 | 池内分三层：必需（★）→ 普通需求（过半且非条件词条）→ 可选（◇ 条件词条 与 个别人要的）；同档按**组内使用人数降序**，人数相同按**组内平均名次权重降序**（权重 = 该词条在这位角色推荐里的名次，见 `subWeights`：第 1 名 1.0、其后 `SUB_RANK_DECAY` 衰减，★ ×1.25、◇ ×`OPT_W`），权重打平（常见于 `subRules.equal` 标了「= 同等优先」的一组）时比**组内平均原始名次**，都相同才退回游戏常规顺序（双暴 → 攻击 → 生命 → 防御 → 精通 → 充能）。**单角色方案下人数恒相等，顺序因此完全等于该角色推荐的原始顺序**——此前第三级是固定的游戏常规顺序，会让角色卡（wiki 原始顺序）与方案页对不上。池生成（`mergeSubUniform`）与展示（`planSubOrder`）共用同一份比较器 `subOrderCmp`，保证「池里的顺序」=「页面上的顺序」 |
| 3 词条圣遗物 | 不模拟（游戏侧行为）：只输出建议过滤条件，不承诺件数 |
| 属性分组着色（追加 + 主要） | 分组配色由 `planColorGroups(p)` 统一分配（按方案角色的次要偏好签名聚类，`GROUP_COLORS` 8 色循环），颜色同时打在**角色名**、**追加属性 chip**（`planSubText` / `planSubOrder`）与**沙 / 杯 / 冠主要属性 chip**（`mainCondText` / `mainColorMarks`）三处，同色即可对应、不需要图例。**退化规则由 `groupMarkPlan(owners, groups)` 一份辅助函数统一裁决**，追加属性与主要属性共用同一套口径：**0 个分组需要 / `owners.length == groups.length`（全组共享）→ 不着色；1 个分组 → 单色（沿用旧观感，不额外堆点）；2–3 个分组 → 逐组一颗色点（`multi`，单 chip 色点上限 `GROUP_MARK_MAX = 3`）；≥4 个分组 → 不着色 + 「N 组需要」角标（`overflow`，`.gp-gn`）**。此前追加属性 chip 只取 `owners[0]` 那一组的颜色（其余分组等于没有提示），现改为 **`owners` 逐个各打一颗色点**——色点用独立元素 `<i class="gp-sub-mark|gp-main-mark" style="--tc:分组色">`，形状同款（7px 圆点），相邻两颗负边距收紧，chip 保持 `inline-block` / `white-space:nowrap` 不换行；色点不带 `pointer-events` 拦截，点击由 `document` 上的 `closest('[data-stat-tip]')` 委托命中父 chip，触屏仍能打开属性小窗。★必需仍是原形态：1–2 个分组需要 → **多色 ★**（`gp-star-multi`，每个分组一颗星）；>2 个分组或整组需求一致 → 退化为单色 ★。**可互换主要属性组**（`SWAP_GROUPS`，当前仅冠部 暴击率 ↔ 暴击伤害）经 `mainUseOf` **同判同色**：只写了搭档的角色在该 chip 上按「次选」计入，chip 着色、hot 角标与 `planMainTip` 三处共用 `mainUseOf` 一个口径，避免同一分组成员因写了不同可互换项而漏色 / 错色。属性小窗（`statTipHTML`）主属性路径复用 `tipRows` 按分组分行、行首色条带 `--tc` 分组色，列出「谁列为首选 / 次选」；**同一属性出现多个色点 = 分别对应多个分组，点开看谁要它**。着色只在渲染层生效：`planCopyText` / `planSubPlain` 等导出路径仍是纯文本、不带颜色 |
| 套装件数需求（4 件套 / 2+2） | 需求角色**全页只出现在方案卡片内**（`.gp-boardrow`，一个方案一块）：同一角色对同一套装可能有多套方案，摊到套装级无法归属到具体方案，故**套装标题行不再列任何角色**，方案卡片头原先那行「本方案角色（共 N 人）」计数行由分栏取代（两栏并集 = 本方案角色，不重不漏）。卡片内按「4 件套」「2 件套」分栏，角色顺序为「**首选 → 备选 → 2 件套**」，同级保持原始顺序；栏目内按次要偏好签名分组（同色 = 同组），按名单首位顺序展示组，同签名成员即使不连续也合并为同一组，弹窗栏标题显示人数与组数。方案卡中每个角色单独成框；`fitPieceBoardGroups()` 测量组容器的实际宽度，最多显示两行，剩余成员折叠为 `+N`，窗口尺寸和语言变化时重算。方案区 `.gp-wrap` 使用容器查询：可用内容宽度 ≥660px 时 `.gp-cards` 固定双列，否则单列，避免被不同层级容器的宽度临界值频繁切列。点分栏空白 → **需求角色弹窗**（`#charTipBox`，第一层）全量列出本方案角色；**点角色 → 固定定位的第二层「角色配装属性」小窗**（`#charAttrBox`，展示件套、主要 / 追加属性）。点第一层空白只收起第二层，点两个弹窗外关闭两层；滚动、切页、缩放或按 Esc 也会收起浮层。复制 / 导出文本不受卡片折叠影响，仍按 `4 件套：A　｜　2 件套：B` 全量输出，与页面共用 `pieceNeedOf` / `pieceColsOf` / `pieceBoardOrder` 口径 |
| 追加属性不能与同部位主要属性相同 | 统一追加属性后，自动剔除与花/羽固定主属性（生命值/攻击力）冲突的项；沙/杯/冠主属性随方案而变，无法逐部位剔除，**照抄时请自行留意** |

最后一条是目前**唯一需要人工注意**的对齐缺口，已在界面上明确标注。

## 7. 设计取舍（记录当时的判断）

| 决策 | 选择 | 为什么不选另一边 |
|---|---|---|
| 方案数量 | 给全部候选 + 手动整理 | 自动压到 3 套必然「存伪」，与工具目标直接冲突 |
| 追加属性 | 方案级统一 | 逐角色一套在游戏内无法表达（一个方案只有一份条件） |
| 合并判据 | 看重要属性重合度 | 纯相似度会被次要属性稀释，导致该合的合不上 |
| 重要度表达 | `=` / `>` 算子 + 排序 | 数值权重用户填不出来，且表达不了「双暴同重要」 |
| 编辑保存边界 | 角色基础信息即时保存，配装使用独立草稿并显式保存 | 基础字段适合随改随用，配装需要保留取消试错能力 |
| 内置数据更新 | 按 `fcanon` 指纹判断改没改，单独保护 `subRules` | 按版本号判断会覆盖用户手工修改 |
| 规则自动填补 | 本地定位启发式 + `source` 区分人工/派生 | 直接把 wiki 数组首项当必需会产生错误锁定 |
| 分发形态 | 单文件 `index.html` | 使用场景是「打开就用」，分发成本 > 工程优雅 |
| 套装简称 | 只在角色卡片用简称（B 口径），方案页 / 导出用全称 | 全站都换简称会和游戏内锁定界面（全称）对不上；全站全称又把卡片撑宽 |
| 简称来源 | 内置人工表 + 用户覆盖优先，无简称则回落全称 | 靠规则自动生成会造出「官网 / 社区都不这么叫」的假短名 |
| 攻略来源 | 只存档链接，工具不解析 | 米游社攻略几乎全是图片一图流，解析不了也不可靠 |
| 卡片配装按钮的定位标签 | 去掉外层全角括号，用亮度分层表达两层语义（套装名 > 大类 > 关键词 > 分隔符） | 全角括号在窄栏白吃约 33px（1440 档 492 条中 18 条、390 档 430 条因此折行）；括号只说明「这是附带信息」，亮度分层更省位也更直接 |
| 配装按钮的选中态 | 只换颜色（金色左轨 + 金字），不换字重 / 字号 | 换字重会让长套装备注重新折行，点一下主推按钮高度就跳一次 |
| 定位标签的断行点 | 分隔符并入它前面那个词的单元，断行点只留在词与词之间 | 「·」「｜」若单独成段，窄栏会优先在分隔符【之前】断行，行首挂出孤立标点（实测 360px 档 9 处） |
| 配装按钮的宽度 | 宽屏按名段汉字数分三档 `min-width` 收缩，窄屏（≤560px）维持等宽 | 等宽撑满会在短名 + 短定位之间留大片空白（实测 1440 档空隙中位 85px、1024 档 131px，448/492 条超 40px）；分档后空隙 → 12px，且同角色内 81% 的方案对可用长度区分（撞档率 100% → 18.9%）。窄屏不收缩不是「不能改」而是取舍：4 个候选在 390 档有收益（撞档 853 → 311–349）但 360 档恶化到 716，因卡内容区仅 140–155px、可行行宽取值被压到 2–5 档，一部分行撑满一部分收缩、线索不稳；且窄屏点选靠触摸、按钮宽即热区宽 |
| 名段折行时定位独占下一行（`.nmwrap`） | 窄屏下名段已占第二行，定位再挤在右侧折成两三行既碎又难读；实测 390 档该定位占 3 行而整段自然宽仅 101.7px（卡宽 155px），本该一行放下 | 定位折行 256 → 193、定位最多行数 3 → 2、文字行数/条 2.84 → 2.65（总高度反而更矮）。⚠️ 标记必须 JS 判定（CSS 判断不了「已折行」，纯 `nowrap` 在 360 档溢出 0.3px）且**只增不减** —— 加标记会让名段变回 1 行、撤标记又变 2 行，来回切换必然死循环 |
| 窄屏（≤560px）改两行版式 + 容器查询收缩 | 手机端每条为「上行名 / 下行位」，定位独占整行右对齐；同时用 `@container(min-width:145px)` 直接量卡内容区宽决定收不收缩 | 定位折行 193 → 0、文字行数/条 2.65 → 2.26、可点面积 5580 → 6687px²。阈值 145px 来自逐 10px 扫 320–480 档：卡宽 ≥145px 撞档 ≤48%、≤136px 恒 84%（可行取值被压到 2–3 个，几何下限，340/350/360 都救不了）。⚠️ `@container` **必须嵌在窄屏 `@media` 内** —— 它自身无断点，宽屏也会匹配，百分比下限会盖掉宽屏 em 档位（实测 1440 撞档 18.9% → 40%） |
| 窄屏 `.nfull` 宽度上限扣掉编号列 | `max-width:calc(100% - 1.5ch - 4px - 12px)` | 基础规则的 `max-width:100%` 是整个按钮宽，卡很窄时（340 档 130px）长名撑到 102.9px 会把编号从 1.5ch 挤扁到 10.2px、名段越界压住编号。⚠️ 改编号为绝对定位虽能修好，但双折行 0 → 46，抵消核心收益 |
| 分档用 `min-width` 而非 `width:max-content` | 只定下限，实际宽度仍由内容与换行决定 | `max-content` 会把 `.wide` 长多套名撑到一行不折、名段逐字拆成 9 行（实测该行 62.5px → 192–281px），是最容易踩的坑 |
| 名称与定位的额外留白 8px（`margin-left`） | 按钮按内容收紧后 `column-gap:4px` 只剩 4px、几乎贴在一起；改 `column-gap` 会连带拉开「编号↔名称」，所以只给定位段加外边距 | 空隙中位 4 → 12px，5 个候选（0/4/8/10/12px）里 8px 是「分得清又不松散」的平衡点；⚠️ `.wide` 的定位段在下一行且自带 `margin-left:0`，必须显式排除否则整段右移 8px |
| 分档只数汉字、不数总字符 | 「如雷 + 宗室」总字符 7 但纯中文 4 字 | 按总字符分档会把它误判成最长档而无谓撑宽；名段实测宽 58.9px，与「苍白之火」同档 |

## 8. 数据来源与可信度

### 8.1 唯一数据源

配装数据的**唯一权威来源**是米游社「观测枢」wiki 角色词条的 **「推荐装备 → 圣遗物推荐」结构化表格**（wiki 编辑手填的文本），通过结构化接口抓取。`subRules` 不是 wiki 原始字段：它是人工校准或基于本地定位的派生解释层，不能冒充远程数据源。

- 搜索：`act-api-takumi-static.mihoyo.com/hoyowiki/genshin/wapi/search`
- 词条：同上 `/entry_page?entry_page_id=`
- 必需请求头：`x-rpc-wiki_app: ys_strategy` + `Referer: baike.mihoyo.com`

词条「攻略推荐」外链的那些米游社文章**几乎全是图片一图流，本项目从不读取**，只在 `out/sources.*` 里作为人工延伸阅读列出。**写来源清单时必须显式标注「非数据源」。**

### 8.2 追加属性写精确值，不套预设桶

每组配装**独立携带**自己的 `subs`，值取自 wiki「推荐装备」的精确数据：

- 不按 `SUB_PRESETS` 预设桶套用——粗桶会让角色显示不符合其真实需求的追加属性；
- 同角色多流派分组各自保留，不会被合并成一个「平均」配装。

`SUB_PRESETS` 只用于新建配装时的默认值与「套用预设」。

### 8.3 已知数据缺口

- 欧洛伦 / 阿罗夏 的 wiki 主词条文本解析不全，主词条沿用了旧值
- 127 个角色里只有 77 个的词条挂了「攻略合集」入口（按 `tools/out/sources.md` 实测：124 条记录中 77 条是攻略聚合页真入口，47 条只有搜索页兜底），其余没有入口
- 少数新角色暂无稳定攻略来源，内置配装是按元素/武器的通用推荐，**角色备注里已标注，请按实际玩法调整**

## 9. 已知局限

1. **追加属性与主属性的互斥无法逐部位剔除**：沙/杯/冠主属性随方案而变，统一追加属性后无法按部位过滤，照抄时需自行留意（已在界面标注）。
2. **候选收敛依赖人工**：工具不替你决定取舍，这是刻意设计，但也意味着结果质量依赖你对角色的理解。
3. **内置配装会随游戏版本过时**：数据按版本手工维护，版本更迭后请自行校正。
4. **数据存在浏览器 localStorage**：清除浏览器数据会丢失，重要配置请先导出 JSON。
5. **GitHub Pages 按域名隔离 localStorage**：同一域名下放两份本工具会互相覆盖数据。

## 10. 维护约定

- **版本号 = 真实日期**（大版本 `YYYY.MM.DD`；同一自然日内每次发布 = 该日大版本下的 `.n` 子版本），由 `build.js` 从 **git 提交时间**自动注入。
  - `src/data.js` 里的 `APP_VERSION` 与 `CHANGELOG[0]` 是占位值，**每次 build 会被覆盖，日期不要手改**；当天第二次发布起才手填 `.n`（`APP_VERSION` 与 `CHANGELOG[0].v` 填同一个）。
  - `APP_VERSION` 必须等于 `CHANGELOG[0].v`，否则更新公告不会弹或重复弹。
- **CHANGELOG 每次发布各记一条，不做同日合并**；界面按大版本聚合展示：数据管理页整表每天一块（块内合并当天各子版本条目并去重），更新公告只弹「最新的未看过的大版本」并把当天未看过的小版本条目合并展示。
- **提交信息里不写日期版本前缀**。
- 改完 `src/` 必须 `node build.js`，否则线上 `index.html` 不会变。
