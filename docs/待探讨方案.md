## S1c · `text-wrap: balance`（定位折行时均衡两行长度）

### 想解决什么

窄屏「定位独占一行」把折行降到 0 之后，仍有极窄档（卡宽 130–140px）放不下整段定位，
定位会折成两行，而**断行点落在 `<wbr>`（词组之间）**，导致两行长度悬殊。

实测（改前 / 360 视口 / 卡宽 140px）：

| 项 | 值 |
|---|---|
| 定位整段自然宽 | 126.3px |
| 可用宽 | 126px（刚好差一点） |
| 实际折行 | 104.3px / 22px —— **两行长度差 79%** |
| 样例 | 丽莎「如雷」位「输出·功能｜元素伤害·冷却」→ 第二行只剩「冷却」两个字 |

### 原型与实测

原型文件：`tools/out/_bal/S1c_bal.html`（仅加一行 `text-wrap:balance`）

| 视口 | 卡宽 | 定位折行数 | 两行长度差 |
|---|---|---|---|
| 360 | 140px | 63 | 79% → **16%** |
| 390 / 430 / 560 | 150–175px | 0（折行已被 S1a 消掉） | — |

**结论：有效**。两行长度差从 79% 降到 16%，是真正的「均衡」。

### 落地时的注意点

1. **浏览器版本门槛**：`text-wrap: balance` 需要 Chromium 114+ / Safari 17.5+。
   不支持的浏览器会**优雅降级**（该属性被忽略，行为回到现状），所以可以安全地直接加。
2. **与 S1a 的关系**：两者互补不冲突。S1a（横向 padding 6→4）已把 360 档的定位折行
   63 → 0，所以 S1c 在**当前**阈值下没有可作用的对象；它的价值在于
   「将来 `.char-grid` 最小列宽若调小、卡宽再窄一点」或「文案变长」时兜底。
   要验证 S1c 到底有没有效，得**临时把 padding 改回 6px** 或用更窄的视口（<360px）复现折行场景。
3. **不要和「允许词内断行」混为一谈**：另有一个原型 S1b（`.bt-w{white-space:normal;word-break:break-all}`）
   同样能让两行看起来平衡（实测差 91%，反而更糟），但它会拆开「元素伤害」这类词 ——
   违反本项目「定位标签词内不许断」的红线，**已否决，不要捡回来**。

## S2 · 「能同行就同行」让短名 + 短定位恢复同行版式（✅ 2026-10-05 .2 已落地）

### 想解决什么

主人提问：「390 和 360 对于短圣遗物名和短定位，为什么不能做到跟桌面端一样两个放在同一行？」

### 实测结论：是几何限制，不是没做

「名段 1 行 + 定位 1 行」在同行下所需宽度 vs 卡内容区宽度：

| 视口 | 卡宽 | 名 1 行的行数 | 放得下同行 | 占比 |
|---|---|---|---|---|
| 360 | 140px | 368 | 125 | **34%** |
| 390 | 155px | 369 | 126 | **34%** |
| 430 | 175px | 369 | 290 | 79% |
| 560 | 149px | 369 | 126 | 34% |
| 768 | 199px | 468 | 433 | 93% |
| 1440 | 237px | 468 | 468 | **100%** |

**窄屏约 2/3 的行放不下同行。** 临界案例：安柏「乐团」需 137px / 卡宽 140px ——
只剩 3px 余量，卡宽 139px 就放不下。

桌面端的「同行」本来就是靠卡够宽（1440 档 100% 可行），不是规则更宽松。

### 原型与实测

原型文件：`tools/out/_bal/S2_fit.html`（JS 量「同行所需宽 vs 卡宽」，放得下就加 `.fitrow`）

| 视口 | 同行行数 | 定位折行 | 溢出 | 压编号 | 行首标点 |
|---|---|---|---|---|---|
| 360 | 125 / 369（34%） | 63 | 0 | 0 | 0 |
| 390 | 126 / 369（34%） | 0 | 0 | 0 | 0 |
| 430 | 290 / 369（79%） | 0 | 0 | 0 | 0 |

技术上可行、零缺陷。**2026-10-05 主人拍板落地**（版本 `2026.10.05.2`）——
理由是 S3（窄屏强制两行）在短名 + 短定位时上行只有一个短名字、整行白掉，观感比混排更刺眼。

落地后实测（492 行 × 17 档视口，`tools/out/_s2.mjs`）：文字行数/条、定位折行数、撞档率、
溢出 / 重叠 / 压编号 / 行首标点 / 超高行**与强制两行逐项完全相同**；变的是：

| 视口 | 同行率 | 按钮均高 | 最小可点面积 |
|---|---|---|---|
| 480（卡 200px） | 95% | 44.2 → 36.8 | 6291 → 5184 |
| 430（卡 175px） | 79% | 44.5 → 38.4 | 5505 → 4536 |
| 390（卡 155px） | 73% | 44.7 → 39.1 | 4875 → 4017 |
| 560（卡 149px） | 34% | 44.8 → 42.2 | 4697 → 3871 |
| 360（卡 140px） | 26% | 44.8 → 42.8 | 6116 → 5040 |
| 340（卡 130px） | 25% | 47.0 → 45.1 | 5679 → 4680 |

**仍然存在的两个已知代价**（落地时已向主人说明并接受）：

1. 同一张卡里同行 / 两行混排；
2. **同行率对卡宽非常敏感** —— 480 视口 95% vs 370 视口 34%，同为手机竖屏、不同机型长相差别很大。
   这是「按卡宽临界放行」的固有性质、不是实现缺陷；要消除它只能改成 JS 逐行判定（历史上的 `.fitrow`），
   那会重新引入与 `.nmwrap` 类似的标记收敛问题，不划算。

回退成本：把窄屏那条改回 `flex:1 1 100%;margin-left:0` 即恢复强制两行（断言里已锁住「不得有 basis:100%」）。
